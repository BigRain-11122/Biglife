# 提交信息编码核验 20261117

口径=T-20261117-01「中文 commit message 被按 GBK 落盘成乱码」。本轮以字节级复核该前提。

## 方法
1. 以 UTF-8 无 BOM 文件承载消息，`git commit -F <file>` 提交（规避 PS 行内 `-m` 参数编码路径）。
2. 用 Python `subprocess.check_output(['git','log','-1','--format=%s'])` 取**原始字节**，分别按 UTF-8 / GBK 解码。

## 结果
| commit | 原始字节解码 | 结论 |
|---|---|---|
| `5b0110`（原判定「GBK 乱码」样本） | UTF-8 解出完整可读中文（len=107） | 存储面无损坏 |
| `157c6ed27`（本轮 -F 提交） | UTF-8 解出完整可读中文（len=110） | 存储面无损坏 |

## 判读
- 控制台把 UTF-8 字节按 GBK 码页渲染时**必然**显示为「瀛橀噺…」形态——该现象属**显示层**，不等于落盘损坏。
- 故 T-20261117-01 所述「被按 GBK 落盘成乱码」**前提不成立**（至少对 5b0110 与 157c6ed27 两例）；真实问题若存在，只在读取/展示侧（终端码页、面板渲染），修法应是显示层统一 UTF-8（如 `chcp 65001` 或 `git log --encoding=UTF-8` 后置解码），**不是**改提交方式或改写历史。
- 生产可用做法（已实跑）：提交消息走 UTF-8 文件 + `git commit -F`，并用字节级解码自证，避免「看起来乱码」被误判为缺陷。

## 边界
- 本核验只覆盖本仓 2 个样本，未穷举全机队；集团层统一（含 bm-a/bm-b 终端码页）仍按原单归集团面。
